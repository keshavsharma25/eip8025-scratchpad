## 2. Agreements reached in this interview

1. **Choose pre-engine atomic claims (Option B), not completion-only Seen updates (Option A).** An authenticated-but-engine-invalid result that only marks Seen *after* verification fixes sequential replay but does not prevent two old-snapshot workers from both entering the engine. A claim must gate engine entry. Workers may still duplicate earlier hashing/BLS work.
2. **Use a pending reservation distinct from permanent Seen.** Following successful authentication and binding, ask the single mutator to atomically claim both the bare-message root `R = hash_tree_root(signed.message)` and prover key `K = (block root, proof type, validator index)`. Only the winner may run the engine. An unauthenticated message never claims a key. On definitive `true`, commit both Seen keys and store the verified bare `.message`; on definitive `false`, commit both Seen keys, store **no** verified proof, and REJECT the first attempt. A claim loser is IGNORE without an engine call. While a claim is pending, same-root or same-prover-key competitors get IGNORE immediately, even if the winner later proves invalid. These are node-local ordering semantics.
3. **Do not block a pool worker waiting for the claim reply.** Stage 1 authenticates/binds on a low-priority worker and sends a request; the mutator makes the live claim decision; only a winner is scheduled as a stage-2 engine task, which sends a finish message. `fork_choice_control/src/thread_pool.rs` places proof work in the low-priority queue. This introduces an extra message/task handoff, not a synchronous wait in each initial worker.
4. **Keep pending claims alongside Seen and verified proofs in `fork_choice_store::Store`; only the mutator grants/removes them.** A worker's immutable `Arc<Store>` snapshot cannot grant a live claim. At claim time, recheck the *live* store for duplicate Seen keys, an already stored verified `(block,type)` proof, required context, and staleness; never grant solely on the worker's older snapshot. Exact live-context comparison/revalidation API is still open.
5. **Use the smallest unique per-claim token/generation, not a token-management framework.** A finish message must match the current ownership of **both** pending keys before it can commit. This fences a late result from an expired/pruned/replaced claim: matching `(B,T,V)` alone would be vulnerable to an old-result/new-claim mix-up. Exact Rust representation remains open.
6. **No timeout-only release while a synchronous verifier might still run.** A deadline may diagnose a stuck task, but must not blindly permit overlapping same-key engine calls. Release after confirmed cessation; finalization may remove a pruned block's claim. A hung call can block that key: document and bound the operational risk rather than promising liveness without cancellation. A late result for a pruned claim is IGNORE and must never recreate pruned Seen/proof entries.
7. **Prune proof bookkeeping in PR2.** Extend Grandine's existing `Store::prune_after_finalization` (`store.rs:5473+`) to the two Seen collections, verified-proof map, and pending claims using a consistent retained-block policy. This is not a new block-pruning system; add tests. The existing payload-root retention at `store.rs:5487+` is a nearby precedent. Exact treatment of the last finalized root and pending claims requires code-level design.
8. **Q13: different eligible validators can claim independently when they submit different bare messages.** Two validators with different message roots and different prover keys for the same `(block, proof type)` may each claim and verify while no valid proof is stored. The pinned gossip keys do not impose a one-pending-proof-per-`(block,type)` gate; a failed proof from A must not suppress B's distinct attempt. If they sign **the same bare message**, its root is the same even though the signed wrappers differ: the second attempt loses at the pending-root claim, receives IGNORE, and never enters the engine. New claims after a verified proof is stored are IGNORE. **Storage rule agreed:** only an engine-valid proof may enter `execution_proofs[B][T]`; an engine-invalid A leaves the slot available for a valid B. Among two concurrently admitted valid proofs, preserve the first one actually stored; never overwrite it. A previously admitted B still gets its engine-based gossip verdict even if A's proof has since been stored (Q14). Distinct keys still require resource limits before live ingress.
9. **Keep `ProofVerifier`'s `bool` signature in this stack.** A typed `Result` would span proof-engine trait, mock/null implementations, tests, and callers and is not a tiny gossip-only change. For now `false` must mean *definitively invalid*, not verifier unavailability. Task non-completion is a separate pending-claim lifecycle concern. Before integrating a real verifier that can fail operationally, revisit the API; do not turn such failure into permanently Seen invalidity. The null verifier opts out before the pipeline.
10. **Security scope:** prioritize avoiding duplicate engine work and uncontrolled overlapping retries, but **do not claim DDoS immunity**. Two keys protect against duplicate root/prover attempts after authentication, not up-to-4-MiB receiving/decoding/hash work, duplicated pre-claim BLS work, many distinct authenticated validators/blocks, unbounded queue growth, or a hung verifier. Defer production-engine fault injection and broad adversarial/DDoS testing until a real engine exists, but retain core claim/race/Seen tests in this stack. Review admission, verifier-concurrency, and queue limits before exposing actual ingress. PR1/this skeleton has no active proof ingress.
11. **Q14: a previously admitted proof gets its own engine verdict even if another proof has since been stored.** If B from a different validator/different message was granted a claim while no valid `(block,type)` proof was stored, and A's valid proof is stored while B runs, B still gets REJECT on definitive `false` or ACCEPT on definitive `true` for accurate peer scoring. Both definitive outcomes commit B's authenticated Seen keys; only a valid proof can be stored, and the first stored valid proof remains in place. A *new* B arriving only after A was stored is IGNORE at the claim/preliminary check without an engine call. This is the agreed local concurrency ordering policy; the pinned sequential spec does not prescribe interleaving of two in-flight verifications. A pruned/invalidated claim is a different case and must not commit on a late result.
12. **Q15: stale snapshot never authorizes a claim.** Stage 1 authenticates/binds using one coherent snapshot; the mutator then checks its *current live store* before granting. If the accepted payload is absent or materially differs from what stage 1 used, decline without running the engine (IGNORE for missing/changed payload, per D1); a known block with missing post-state follows D2's REJECT. Do not redo expensive authentication on the mutator. This establishes freshness at claim grant, **not** a promise that the store cannot change while the engine runs.
13. **Q16: relevant context changes after grant invalidate finish-time application.** After the stage-2 engine task returns, the mutator checks both-key token ownership and that the live block/post-state/accepted payload still matches the authenticated, bound context. If the claim was pruned or relevant context is unavailable/changed, discard the token and signal IGNORE: no Seen or verified-proof insertion, including on a late `true`/`false`. Another validator storing a valid proof while this claim runs is **not** such invalidation: preserve Q14's verdict for an already admitted different-message proof. An unrelated store-snapshot update is also **not** stale context by itself. Context identity/comparison and operational cleanup still need precise implementation design.

### The two-stage timeline (sketch, not code)

```text
S0: Seen={}, pending={}, verified={}; two workers see the same old snapshot.
worker A: pinned preliminary checks + authenticate + bind X -> ClaimRequest(Rx,K)
worker B: pinned preliminary checks + authenticate + bind Y -> ClaimRequest(Ry,K)
mutator:  check LIVE state, grant A token=1 for both Rx and K
          deny B (K pending) -> IGNORE; no engine(Y)
worker C: stage-2 task(token=1) calls engine(X) -> false
mutator:  if token 1 still owns Rx and K and context is usable:
          remove pending, mark Rx and K Seen, store no verified X -> REJECT X
later Y:  ignored via Seen K without an engine call
```

If X/Y are from different validators but have the **same bare message root**, the second cannot claim: the pending-root check ignores it before any engine call. If they have different roots and no valid proof is stored, **both may claim** (agreed Q13). If X's envelope/signature fails authentication, it does not claim; a later genuine attempt is not suppressed. The finish-time outcome for concurrently admitted distinct-validator *different-message* proofs is agreed in Q14: each receives its engine verdict, but cannot overwrite a valid proof already stored.

### Why two existing Grandine examples are *parallels*, not a reusable solution

- `Store.accepted_execution_payload_envelopes` is written after payload-envelope acceptance and pruned at finalization (`store.rs:300`, `4917+`, `5504+`); it is not a pre-engine paired claim.
- `Store.sidecars_construction_started` marks reconstruction underway, removes on reported failure, and prunes at finalization (`store.rs:314`, `6750+`, `5508+`; `operation_pools/src/blob_reconstruction_pool/tasks.rs:122+`). It resembles pending work but has neither an atomic `(R,K)` claim nor a completion token.
- `Store.seen_gossip_attestations` uses a mutex for shared Seen data and prunes by epoch (`store.rs:193`, `5385+`, `5435+`); its gossip policy is different.

## 3. Still open — decide before writing PR2/PR3 code

- **Already-admitted result after context changes:** specify which non-storage context changes (pruning, cache eviction, changed payload/state) invalidate a previously granted token; do not confuse this with another validator storing a valid proof (Q14 is settled).
- **Snapshot/live-context compatibility details:** define the stage-1 context identity and cheap live comparison used to enforce agreed Q15 without re-running expensive authentication on the mutator; preserve the pinned ordering of IGNORE/REJECT checks. A live check must not silently admit a proof bound to a different payload. D1 cache miss and D2 missing-state rules still apply.
- **Failure cleanup:** how to learn that the synchronous worker has *actually stopped* on panic/cancellation; how to surface stuck claims without timer-only release; shutdown/restart semantics. `bool` cannot encode transient verifier failure. Do not promise an absolute engine-call bound across crashes or restarts without proving it.
- **Admission/resource policy:** enforce an appropriate finite bound on pending claims, verifier tasks, queue bytes and work before live gossip ingress is enabled. Decide what to report when the bound is reached, without inventing a spec REJECT for an operational capacity failure. Not all of this necessarily belongs in PR2.
- **PR boundaries:** design 0004 currently describes a single read-only `validate_execution_proof_gossip(..., verifier)` plus `apply_execution_proof` in PR2 and task wiring in PR3. A pre-engine claim requires a stage-1/stage-2 split and claim/finish mutator messages; revise the design and PR scope explicitly. Do not call PR2 end-to-end if stage-2 wiring is in PR3.
- **Core tests:** invalid authenticated proof -> first REJECT, both Seen, no verified proof; sequential replay/new bytes same prover -> IGNORE, one engine call; bad signature -> no claim/Seen; two simultaneous identical messages and same-prover different messages -> one admitted engine call; two distinct provers -> independent admission; stale snapshot/live duplicate; token mismatch/late finish after pruning; finalization cleanup; null verifier bypass. Use a controllable mock/barrier rather than await a production engine.
